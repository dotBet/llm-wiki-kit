LLM Wiki

Compiled memory for long-lived work. Markdown, git, and the coding assistant you already use.

Vanilla knowledge, not a new product stack

The leak

Delivery knowledge does not compound.

  • Chat sessions and tickets answer a question once, then disappear.
  • The next engineer—or the next agent—starts over on the same platform handbook.
  • Shared drives go stale; search finds documents, not decisions.
  • Retrieval over a pile re-derives the answer every time, with no memory of what you already settled.
LLM Wiki

The idea

Compile once. Keep it current. Ask the wiki first.

Working memory

An LLM incrementally compiles sources into a small, linked Markdown wiki—the map your team and agents query next time.

Source of truth

Originals stay immutable. The wiki is compiled knowledge, not a chat transcript and not a second copy of every PDF.

Query path

Start at the catalog, follow links, then open raw files only to verify, fill a gap, or resolve a conflict.

Origin

The pattern follows Andrej Karpathy’s LLM Wiki idea: a persistent Markdown knowledge base maintained by an agent, reviewed by people.

LLM Wiki

Vanilla on purpose

No new platform. A repo you already know how to run.

  • Markdown files in git—the system of record, with a normal review trail.
  • Works with the coding assistant you already use (Cursor, Claude, Copilot, Codex, and peers).
  • People browse in GitHub or Obsidian. The agent writes Markdown; humans approve the diff.
  • Not a wiki SaaS to license. Not a custom vector pipeline required for the core loop.

What you get

A compiled knowledge base the next engagement can open.

Answers with provenance

Reusable answers cite sources. Inferences are labeled. Gaps stay visible instead of sounding finished.

Decisions with rationale

Dated choices live as pages: why we named tables this way, what is still open, what superseded what.

A map

A catalog of concepts, entities, and operations so an agent does not load the whole vault to answer one question.

A timeline

An append-only log of ingests, queries, and maintenance—so you can see how the wiki grew.

The loop

Ingest, compile, ask, keep honest.

Ingest

Capture raw material. Extract claims, terms, and open questions.

→

Wiki

Update existing pages before creating new ones. Link related ideas.

→

Query

Answer from the wiki first. File reusable answers back.

→

Lint

Fix drift, dead links, duplicates, and unsourced claims.

LLM Wiki

Trust

Claims are labeled. People still own the merge.

  • Sourced — non-obvious facts point back to a captured document or note.
  • Synthesized — cross-page inference is marked as such, with contributing pages.
  • Uncertain — missing evidence stays an open question, not a confident sentence.
  • Human review on the git diff is the control. The wiki is not allowed to silently rewrite originals.

Proof in this repo

Same pattern, one domain: a Fabric lakehouse handbook.

  • This repository uses the wiki on ArganoRun—an enterprise lakehouse on Microsoft Fabric—not as the product we are selling.

LLM Wiki

Appendix · architecture

Three layers, all files.

sources/

Immutable originals and source notes. Ground truth. Do not silently edit after capture.

wiki/

Compiled, linked Markdown: concepts, entities, decisions, operations, plus a catalog and a log.

Operating contract

How agents ingest, query, and lint. Lives beside the wiki, not inside the portable knowledge bundle.

Progressive load

Start at the index. Open only the pages needed. Avoid stuffing the whole vault into one prompt.

LLM Wiki · technical

Appendix · any agent

One contract. Thin adapters. Portable wiki.

  • Coding agents load a single operating contract; vendor files are pointers, not a second rulebook.
  • Chat UIs: paste the contract and the wiki index; if the model cannot write files, it emits diffs you save.
  • The compiled wiki/ tree is a portable Markdown bundle (OKF-shaped)—interchange without locking to one vendor.
  • You keep git, review, and the assistant your engineers already opened this morning.
LLM Wiki · technical

Appendix · limits

What we do not claim.

  • Not a overnight replacement for your lakehouse, intranet, or Confluence.
  • Not automatic truth: unsourced claims can persist if lint and review are skipped.
  • Value shows after a few real ingests—not on an empty wiki on day zero.
  • Poor page boundaries still create duplicates. Maintenance is part of the work, not a side quest.
LLM Wiki · technical

How we would start

One bounded domain. A handful of sources. A live question.

  • Pick a handbook that already hurts—one platform, one program, not the whole enterprise.
  • Ingest three to five source documents into the repo and compile them into the wiki.
  • Run a real Q&A session against the catalog. File anything reusable back into pages.
  • Leave the git repository as the handoff: sources, compiled wiki, and the operating contract.
